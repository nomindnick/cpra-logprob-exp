EXP-0000 · Summary

One token is enough to rank the pile. Where to cut it is the hard part.

This project tested whether a small language model running on one desktop can pre-screen email for a California Public Records Act request. This page explains all of it from the start: the idea, the data, every test, the detours, and what the numbers do and do not show.

      Part IThe idea
      EXP-0001

      A broad search returns a pile, and people sort it by hand

      When a California Public Records Act (CPRA) request arrives, the agency usually runs a broad keyword search over its email. The terms have to be broad, or responsive records get missed. Broad terms also pull in a large volume of email that has nothing to do with the request.

      Staff then read the results and decide, one email at a time, whether each is responsive, meaning it is a record the request asks for. Only after that does exemption review begin. The hand sort is the bottleneck.

      Why local

      The records can't go to a vendor

      Search results include student files, attorney–client material and personnel records. A model that runs on the agency's own hardware never sends them anywhere.

      Why not the 2025 approach

      It took 30 to 60 seconds per document

      An earlier attempt had small local models write out a JSON answer with a decision, a confidence and reasoning. On a CPU-only laptop that was too slow to use at real volumes.

      Scope

      Responsive is not the same as disclosable

      An exempt email is still responsive. The experiment only asks whether an email is something the request covers. Whether it can be withheld is a separate, later step.

      EXP-0002

      Stop the model after one token and read its odds

      A language model writes one token at a time. A token is a word or a piece of one. Before it writes each token, the model gives a probability to every token it knows. Normally the software picks one, moves on, and throws the probabilities away.

      This experiment keeps them. The prompt shows the model a request and one email and asks for a one-word answer, yes or no. The model reads the prompt once. The run stops at the first token, and the score comes straight from the probabilities on yes and no. Nothing is generated. The log of a token's probability is called a logprob, which is where the project gets its name.

      Known mechanism

      Rerankers already work this way

      Search systems use language models as rerankers by reading the same yes/no probability. That is evidence the idea is sound, and it was the planned baseline.

      Where the idea came from

      Jev, a hosted decision model

      TypeSafe's Jev returns a probability for a yes/no question about a document. It is fast and cheap, but it is an outside service. The question here was how close a local model can get.

      Part IIFirst pass on real productions
      EXP-0003

      2,462 real emails from four San Diego County requests

      The County of San Diego posts what it produces in response to records requests. The first dataset took every email from four of those productions. Each email was paired with each of the four requests, which gives 9,848 pairs.

      The first labels were crude. An email counted as responsive to the request it was produced for (2,462 pairs) and not responsive to the other three (7,386 pairs).

      A limit that follows the project to the end: agencies publish what they produced, never what they screened out. So the non-responsive examples here are other requests' records. Most are easy to tell apart, and that flatters every model. Section 14 measures how much.

      EXP-0004

      The first run worked, and the spot check said the labels were the problem

      On September 22 a 4-billion-parameter Qwen model scored all 9,848 pairs in 159 minutes, about one second each. It ranked well. Its AUROC was 0.933, where 1.0 is a perfect ranking and 0.5 is a coin flip. But to keep 98% of the responsive emails it could clear only 35% of the rest. A fixed cutoff of 0.5 kept only 72% of the responsive emails.

      What reading the 100 worst errors showed

      The 50 lowest-scoring "responsive" pairs and the 50 highest-scoring "non-responsive" pairs were read by hand. None of the four findings was simply a model mistake.

      Finding 1

      Some requests are about people

      Request 25-3152 asks for all communications of planning-group members. An SDG&E wildfire-fair notice, a password reset and "RE: hi" are all plausibly responsive. The model judged topic and scored them near 0.02. It also has no way to know who the members are.

      Finding 2

      One request never says what it wants

      The portal text for 25-4697 is "Please see the attached Public Records Act request." The model still reached 99.5% recall from the requester's follow-up message and the subject lines.

      Finding 3

      A garbled request reads as a broad one

      25-5982 is a list of mailboxes and keywords with typos. Recall was 100% but only 6% of the other email was cleared. A plain keyword filter would handle this request better.

      Finding 4

      Near neighbors score high, as they should

      The highest-scoring negatives for the Alpine request were Harmony Grove emails. Same county, same kind of land-use dispute, a different community.

      Five models, same pairs

      Detour

      Gemma silently returned garbage

      On this build the Gemma models would slip into a state where the first token became <unused49> and stayed there until the model was unloaded. One full run produced 9,842 garbage rows out of 9,848. The fix was a canary: rescore a fixed pair every 100 calls and reload on drift. Clean reruns needed 3, 123 and 272 reloads.

      Hardware check

      A CPU laptop ranks the same and takes 13 times as long

      On a Framework 13 without GPU help, the 4B model took 12.9 seconds per email against 1.0 on the desktop. On a 500-pair subset AUROC was 0.945 against 0.942, though the desktop side of that comparison ran in the backend state later found faulty (section 8). Ranking carried across hardware. A fixed cutoff did not. The full 9,848 pairs would take about 40 hours. Laptop runs were dropped on November 4.

      Part IIIA harder, purpose-built test
      EXP-0005

      The golden set: 496 pairs built to be hard

      The spot check exposed two weaknesses. "Produced" is a noisy label in both directions. And the non-responsive examples were too easy. So on September 25 the project moved to a smaller set, designed to probe specific failures, with Opus pre-labels and a lawyer deciding the doubtful ones. The spec calls it the golden set.

      It covers two requests, one of each type: 24-409 is about a subject, and 25-3152 is about who is writing to whom. Each pair is one email checked against one request. 270 pairs use real emails. That is 259 different emails, because 11 are checked against both requests. The other 226 pairs use synthetic emails: Opus edited 130 real emails, keeping the sender, the signature block and the shape of the thread, and changing the substance according to a recipe. 230 were written and 4 were dropped.

      How the labels were made

      • Opus pre-labeled 420 real emails and gave a reason for each.
      • You checked every pre-label that disagreed with what the County produced, plus a random sample. All 81 in the sample were confirmed.
      • A second model pass reviewed each synthetic email, and you ruled on every one it flagged.
      • Labels that the models' own reasoning or the later misses analysis called into question were re-read and decided. 136 human calls were applied in all, 14 of them on emails that are not in the final set.

      That leaves 185 of the 270 real pairs and 189 of the 226 synthetic ones without an individual human call. The random check puts the disagreement rate under 3.6%, but it was done on a page that showed Opus's suggestion, so it bounds disagreement with a visible suggestion. A blind second reader would settle it.

      EXP-0006

      Two rules decided the hard calls

      Some labels were legal judgment calls about the scope of a request. You made them as the attorney, and two rules came out of the decisions. They point in opposite directions, and the difference is who created the ambiguity.

      Rule 1

      Literal, where the requester cast the net

      When a request covers the communications of named people or a named group, every such communication is in. That includes mail the requester plainly was not after, such as a mass mailing where one member is among thirty recipients.

      The problem is the requester cast too wide of a net, but our responsibility is to use that net.
      Rule 2

      Intent, where a keyword is ambiguous

      A term the request uses in one sense does not bring in email that uses it in another. In 24-409, "RDF" is the Regional Decarbonization Framework, so refuse-derived fuel is out. The CPRA allows reasonable interpretation and puts a duty on the agency to help the requester clarify.

      I think its borderline bad faith to turn "RDF" into a keyword search and to give a requestor documents they didn't want, without at least clarifying with the requestor first.

      One exception sits under Rule 1. A purely personal message is not a public record at all (City of San Jose v. Superior Court (2017) 2 Cal.5th 608), so a fishing trip between two members stays out.

      EXP-0007

      Thirteen configurations, the same 496 pairs

      Names in the charts follow one pattern. The number is the model's size in billions of parameters. The suffix is how the answer was taken: lp for the yes/no score from section 2, json and jsonR for generated answers.

      3 configurations · local

      Stock Qwen, yes/no score

      4b lp · 9b lp · 27b lp

      qwen3.5:4b, qwen3.5:9b and qwen3.8:27b as downloaded, compressed to 4 bits per weight (Q4_K_M). The method under test.

      3 configurations · local

      Stock Qwen, JSON verdict

      4b json · 9b json · 27b json

      The 2025 approach. The model writes a verdict, a confidence and its reasoning. The score is the confidence if it said responsive, and one minus the confidence if not.

      3 configurations · local

      Stock Qwen, reasoning first

      4b jsonR · 9b jsonR · 27b jsonR

      The same JSON answer with the reasoning written before the verdict, enforced by a schema. Tests whether thinking first helps.

      3 configurations · local

      d3 decision models

      d3-4b · d3-9b · d3-27b

      The vLLM Semantic Router decision models, built on the same three Qwen bases, at 8 bits per weight. They read the whole prompt at once and return P(yes) directly.

      1 configuration · hosted

      Jev

      Jev

      TypeSafe's decision model (jev-1.14.0) through its API. Scores come back with two decimals, and its time includes the network. Using it sends the records to a third party.

      The machine

      One Strix Halo desktop

      128 GB of unified memory and a Radeon 8060S integrated GPU. Ollama 0.40.13 on ROCm 7.2. Context of 8,192 tokens, thinking off, temperature 0, one email at a time.

      System prompt for the stock modelsYou are a public records analyst for a California county. You will be shown a California Public Records Act (CPRA) request and one email from the county's email system. Decide whether the email is responsive to the request, meaning it is a record the request is asking for. If the request covers communications sent or received by named people or groups, an email to or from one of them is responsive whatever its subject, unless it is purely personal and has nothing to do with public business. Do not consider whether the email might be exempt from disclosure; that is a separate question. Answer with a single word: yes or no.

      The highlighted sentence was added on October 31, and the runs were repeated with it by November 1 (section 12). The request and the email follow in the user message. The model sees the headers, the attachment names and up to 8,000 characters of the body. It never sees attachment contents.

      EXP-0008

      Detour: the GPU backend was corrupting the small models

      The first golden-set runs of the 4B and 9B models, on October 5, looked plausible. The JSON reasoning gave the problem away. Now and then the model's explanation described an email it had scored one to four rows earlier.

      Fault 1

      State leaked between requests

      After the model scored email A, it was asked to list email B's attachments. It answered with A's file name. The 9B scored one email 0.19 with nothing before it and 0.90 right after another email.

      Fault 2

      Long prompts arrived garbled

      Reloading the model before every call stopped the leak and exposed a second fault. Prompts over 2,048 tokens were corrupted. In one run the 9B described 56 of 172 long prompts as garbled, for example as "a series of '!' characters".

      Both symptoms matched open upstream reports for this model architecture on AMD's ROCm (ollama/ollama#18528, ggml-org/llama.cpp#29092). The workaround suggested there made things worse on this build: the 9B named Prague as the capital of France.

      The fix was one setting, num_batch=8192, which processes the whole prompt in a single batch. With it, scores were identical on all 496 pairs with or without a reload, none of 2,980 JSON answers mentioned garbled input, and the results matched a CPU-only reference run.

      • The canary did not catch it. Its reference score was taken in the same faulty state. What caught it was reading the model's reasoning, then a cross-request probe, a reloaded-against-cached check and a CPU reference.
      • The 27B model was never affected.
      • Earlier results were marked. The sweep and first-run Qwen numbers in section 4 came from the faulty state and carry correction notes.
      • The fault is gone on Ollama 0.40.13 (rechecked November 4), so the final 4B and 9B yes/no runs use the default batch again, which is faster. Their JSON runs stayed on the large batch.

      The lesson for any local deployment is that the backend needs its own validation. A model that is quietly reading a corrupted prompt still returns a confident number.

      Part IVResults
      EXP-0009

      Results: the two largest local models lead, and the yes/no score beats a written answer

      Two numbers carry most of this section. It helps to pin them down first.

      How to read it

      AUROC measures ranking

      Pick one responsive email and one non-responsive email at random. AUROC is the chance the model scores the responsive one higher. 1.0 is a perfect ranking and 0.5 is a coin flip. It needs no cutoff.

      How to read it

      "Cleared at 98% recall" measures the payoff

      Set the cutoff as high as it can go while 98% of the responsive emails still score above it. Then count the share of non-responsive emails below it. Those never reach a reviewer. On 289 responsive emails, 98% allows five misses.

      • The two 27B models lead and can't be told apart. The d3-27b is ahead of the stock 27B by 0.006 AUROC and 5.3 points of clearance, and both intervals include zero.
      • Clearance is noisier than ranking. With five misses allowed, a few borderline emails move it by several points. The jump from the 4B to either 27B model is solid. The step from 4B to 9B is not established.
      • Jev sits with the small local models on quality (AUROC 0.917, 64% cleared) and is far faster than anything local.
      • Real email against real email scores AUROC 0.982 to 1.000. That says more about how easy the real non-responsive emails are than about the models. On the Alpine request alone, the 4B model clears only 23 of 60 real non-responsive emails at 98% recall. See section 14.

      Explore the scores

      Speed against payoff

      EXP-0010

      A written verdict is one decision. A score is a dial.

      The 2025 approach asked the model to write its confidence as a number. In practice the model has a few favorite numbers. Each JSON run used two to five distinct confidence values. The 27B wrote 0.95 on 266 emails, 1.0 on 213 and 0.98 on 15. Not one of the 2,972 JSON scores falls between 0.2 and 0.8.

      So a JSON answer gives one operating point, the verdict itself, and no way to trade recall against workload. It is also confidently wrong: when the 9B said "not responsive" with confidence of 0.95 or higher, it was wrong 24% of the time.

      A fair comparison holds the workload fixed. Set the score's cutoff so it flags exactly as many emails as the JSON verdict did, then compare who was right where the two disagree.

      Does reasoning first help?

      One fair objection to the JSON test is that the model gave its verdict before it reasoned. So the runs were repeated with the reasoning written first.

      EXP-0011

      Where it breaks: near misses, and dates most of all

      The pooled numbers hide a split. Every model clears the easy non-responsive emails. The cost sits almost entirely in the synthetic near misses.

      Size effect

      Small models don't check the date

      An on-topic email dated outside the window passes the 4B, the 9B and Jev 85 to 90% of the time at a cutoff of 0.5. The two 27B models pass 15%. This is the clearest thing extra size buys.

      Good news

      Exempt is not mistaken for non-responsive

      At the default cutoff the yes/no runs catch 98 to 100% of the privileged and personnel emails, against 90 to 93% of ordinary real ones. The instruction to ignore exemption holds.

      Unsolved

      Purely personal mail between named people

      Six emails in the set are personal mail to or between planning-group members. No model reliably leaves them out. Section 12 covers the attempt to fix that.

      EXP-0012

      The Alpine request asks about people the model has never heard of

      Request 25-3152 covers every communication of "any member" of the Alpine Community Planning Group. It does not name them. In October the 27B's lowest-scoring responsive emails were almost all of this kind: a meeting agenda, a district attorney's event invitation, a password reset. They are responsive only because of who sent or received them, and the model was reading the request as if it were about a subject.

      Two fixes were tested. Prompt 2 adds the sentence highlighted in section 7, which tells the model that mail to or from a named person or group is responsive whatever its subject. The roster appends the list of members, their roles and their email addresses to the request.

      Prompt 2 alone

      The small models just say yes more

      Without a roster the new sentence barely changes the 27B's ranking (AUROC 0.975 to 0.977). The 4B and 9B treat it as a push toward yes on both requests. Their recall at 0.5 rises from 80% to 93–95% and they clear 5 to 11 points less.

      Prompt 2 plus roster

      The rule works once the model knows the names

      With the roster attached, prompt 2 lifts the 27B's AUROC on the Alpine request from 0.978 to 0.994 and its clearance from 82% to 93%. The emails that scored near zero move up.

      The exception

      "Unless it is purely personal" does nothing

      Of the six personal emails, the 27B passes five at its 98% cutoff under either prompt, with or without the roster. The models apply the rule and skip the exception. Those stay with human review.

      The roster has two costs. It adds 1,330 tokens to every prompt. The stock models read it once and reuse it, so their time per email does not rise. The d3 models reread it on every call, which adds 0.8, 1.2 and 3.7 seconds per email at the three sizes. They ran at the large batch setting, where the small stock models also stop reusing it, so the runs show that the d3 models reread the roster and do not show why. Jev's time rises by 9 milliseconds.

      It also changes the scores. With the roster attached, the d3-27b's 98% cutoff on the same emails moves from 0.54 to 0.91. A prompt with a roster is a new configuration, and it needs its own cutoff. The next section is about why that matters.

      Part VHow much to trust it
      EXP-0013

      The cutoff problem: every number so far was set with the answers in hand

      Each "cleared at 98% recall" figure above used a cutoff picked after looking at the labels. A real deployment has to pick the cutoff first, on a request nobody has labeled. This is the weakest part of the result, and the part a public claim has to be most careful about.

      The two requests do not agree on where the cutoff belongs.

      The default

      0.5 holds for one model only

      At a plain cutoff of 0.5 the d3-27b missed 0 of 146 and 1 of 143. Every other score model missed at least five responsive emails on one of the requests. That one success was noticed after the fact.

      A small labeled sample

      Fifty emails can't certify 98%

      Set the cutoff at the lowest-scoring responsive email in a random sample of 50. It reaches 98% recall on the rest about half the time on this set, and about one time in five when 20% of the pile is responsive. Ninety percent assurance needs about 114 responsive emails in the sample.

      A roster

      Changing the prompt changes the cutoff

      A cutoff fitted on the Alpine request with the roster attached, then used on the water-report request, missed 84 of 146 responsive emails for the d3-9b and 76 for the d3-4b.

      The best-supported policy so far

      The findings mark this part low confidence. The best-supported rule is a fixed cutoff for each model and each prompt. Fit it on every labeled request available, then step it down one notch for margin. On each new request, check a random sample of what was screened out. On these two requests that rule gives the following.

      These data can't show any cutoff policy to be safe on a third request. Before first use, an agency would need to label at least one of its own requests of each type and check the cutoff against it. The sample check only catches large failures. With 20% of the hits responsive, a sample of 50 catches a cutoff that misses 10% of responsive emails with probability 0.64, and one that misses 5% with probability 0.39. A sample of 200 raises these to 0.98 and 0.87.

      EXP-0014

      How hard is the test? It depends which non-responsive emails you count

      The headline mixes two very different kinds of non-responsive email. The 120 real ones are other requests' records, and 118 of them fall outside the date window of the request they are paired with. A keyword search with a date filter would never have returned them. The 87 hard negatives are synthetic and built to be near misses.

      Splitting the test three ways shows how much each kind carries the result.

      • The synthetic responsive emails behave like real ones. A synthetic positive outscores a real positive about half the time (0.46 to 0.56).
      • The hard negatives carry the difficulty. A hard negative outscores a real negative 87 to 99% of the time.
      • The near misses read as real, mostly. In a spot read of 30 emails by one reader on the October 31 labels, 9 of 10 hard negatives and 7 of 10 synthetic positives passed as real. Two of those hard negatives have since been relabeled. They are minimal edits of real emails, which makes them close pairs by construction.
      • The checks are not independent of the generator. Opus wrote the synthetic emails and the first labels, and AI analysts from the same family did the realism reads.
      EXP-0015

      What it would save, as a scenario

      This is an estimate built on assumptions, and none of it was measured. A keyword search returns 10,000 emails. 20% are responsive. Half of the rest are as easy as the real negatives here and half are as hard as the synthetic ones. A reviewer takes 30 seconds per flagged email. The machine scores one email at a time.

      At a plain 0.5

      Most models would miss over a hundred

      At a cutoff of 0.5 the same scenario loses 111 to 145 responsive emails per 10,000 for Jev and the three stock models. The d3-27b loses 7.

      Calibration

      The scores rank. They are not probabilities.

      No model's 0.7 means "70% likely responsive". The test set is 58% responsive by design. On a request where 10% is responsive, a score that means 0.5 here would mean about 0.07. A cutoff has to be set by policy.

      Part VIWhere it stands
      EXP-0016

      Scorecard against the original hypotheses

      H1 · Speed

      The yes/no score is much faster than a JSON answer

      Supported

      2.6 to 6.2 times faster, and never the hoped-for ten times. Writing the JSON alone takes longer than the entire yes/no call at every model size.

      H2 · Screening

      Keep 98% of responsive email and clear more than half of the rest

      Met in-sample only

      All seven score models clear 53 to 83% with the cutoff fitted to the answers. It is not shown for a cutoff set in advance. Against near misses inside the date window no model reaches half (16 to 48%).

      H3 · Trustworthy scores

      A higher score means a more likely match

      Partly

      Broadly true as a ranking. No score is a calibrated probability, and what a score means would shift on a request with fewer responsive emails.

      Three more hypotheses were set aside. H4, a reranker baseline, and H5, the effect of compression level, were never run. H6, other hardware, was checked once on the laptop and dropped on November 4.

      EXP-0017

      What this does not show

      Caveats

      • Two requests from one county, one of each type. Request type can't be separated from the particular request.
      • Every clearance figure is in-sample. Cutoffs set in advance did worse.
      • The real non-responsive emails are not search hits. The project has no real near misses from inside a request's window.
      • One generator wrote every synthetic email, and the checks on them were not independent of it.
      • One adjudicator. The scope calls are one lawyer's reading. Under a narrower reading of "one member among many", the cutoffs would move, and the d3-27b's lead on the Alpine request with the roster would go from +6.6 points to −0.8 (interval −12.0 to +5.6).
      • One run per configuration. The 4B's clearance was 53% in one run and 48% in another with the same AUROC.
      • Backend noise is not in the intervals. The bootstrap resamples emails from one run of each model. Several significance results sit between 0.03 and 0.09, close enough to move under a reseed.
      • Prompt 2 was written after reading this set's misses, so its gains are in-sample.
      • Small counts. 146 and 143 responsive emails per request, so 98% allows two misses on each.
      • Attachments are invisible. The models see file names and never the contents.
      • The d3 comparison is confounded. The d3 and stock packages differ in compression level, serving runner, batch setting and prompt delivery all at once. A gap between them is not proof of better training.
      • Jev's data terms were never reviewed. The test used already-public records and synthetic edits. Sending live search results to any outside service is the problem a local model avoids.
      • One machine, one email at a time. Parallel scoring and other hardware weren't measured.

      Open work

      • A third and a fourth labeled request, one of each type, to test the fixed-cutoff policy out of sample.
      • A labeled sample of a real keyword-search result. It would give the true share of responsive email, the real mix of easy and hard negatives, and real near misses.
      • A blind second reader on a sample of the labels.
      • Untangling the d3 differences: a d3 run at the default batch, a stock 27B at 8 bits, and an uncached stock 27B run.
      • Repeat runs of Jev and the d3 models to measure run-to-run noise.
      • A design for the sample check on each new request.
      • A narrower named-correspondent rule, tested on a request the prompt has never seen.

      EXP-0019

      Glossary

      Responsive
      The email is a record the request asks for. It says nothing about whether the email can be withheld.
      Token
      The unit a language model reads and writes: a word or a piece of one.
      Logprob
      The logarithm of the probability the model gives a token. The score here comes from the logprobs of "yes" and "no" at the first step of the answer.
      Score
      P(yes) divided by P(yes) plus P(no). It runs from 0 to 1.
      Cutoff
      The score below which an email is screened out. Also called a threshold.
      Recall
      The share of responsive emails that score at or above the cutoff and so reach a reviewer.
      Cleared, or eliminated
      The share of non-responsive emails that score below the cutoff. This is the work saved.
      AUROC
      The chance that a random responsive email outscores a random non-responsive one. 1.0 is perfect, 0.5 is chance.
      In-sample
      A cutoff chosen using the same labeled emails it is then graded on. It flatters the result.
      Golden set
      The 496 request and email pairs used for every result from section 5 on. Labels are Opus pre-labels, with the doubtful ones decided by one lawyer.
      Hard negative
      A synthetic near miss: an email built to look responsive and not be.
      Roster
      The list of Alpine planning-group members, roles and addresses, appended to request 25-3152 in some runs.
      4b, 9b, 27b
      Model size in billions of parameters. Larger is slower and usually better.
      lp, json, jsonR
      How the answer was taken: the first-token score, a generated JSON answer with the verdict first, or one with the reasoning first.
      d3
      The vLLM Semantic Router decision models, tuned to return a yes/no probability. They run locally.
      Jev
      TypeSafe's hosted decision model. The idea for this project came from it.
      Q4_K_M, Q8_0
      Compression levels for model weights: about 4 and 8 bits per weight.
      Calibration
      Whether a score of 0.7 means the email is responsive 70% of the time. Here it does not.
      EXP-0020

      Next: one claim for the video

      A 60 to 90 second video can carry one idea. These are three candidates the evidence supports. Each would use synthetic emails only, and each keeps the framing we agreed on: a promising local pre-screen, and no substitute for review.

      One word is enough

      The model was about to say yes or no. Reading its odds at that moment is 2.6 to 6.2 times faster than letting it write an answer, and it sorts the pile better.

      Visual: the token bars, then the dots sliding into place.

      Caveat it must carry: ranking is not the same as a safe cutoff, and this is one model family with these prompts.

      A desktop can clear most of the pile

      On a 496-pair test set, a model on one desktop kept 98% of the responsive ones and cleared 77 to 83% of the rest. Nothing left the building.

      Visual: the cutoff slider sweeping across the strip.

      Caveat it must carry: cutoff chosen after the fact, two requests, one reviewer's labels, 226 synthetic emails written by another model, and 43 to 48% against near misses.

      The model ranks. The lawyer sets the line.

      The ranking is very good. The hard part is where to cut, and the right cutoff differed between two requests. That part is still a judgment call.

      Visual: the two-request strip with one cutoff failing on the second.

      Caveat it must carry: none needed. The caveat is the claim.
